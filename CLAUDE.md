# fynix-leads

Lead generation tracking portal. A client reviews leads that the Fynix team submits and approves, rejects or asks for clarification. An agency does the work behind Fynix. Fynix runs both. The foundations (database, sign-in, domain, Fynix set-up) and the client, supplier and agency portals are built on a real database: leads and their lifecycle, meetings, messaging and chat groups, and analytics. What is left before production is in `docs/deploy.md` (server set-up, scheduled jobs, gates G1 and G2).

**Wording (owner decision, 2026-11-24):** the supplier role is called **Coordinator** in everything a person reads: menus, titles, forms, messages and errors. Code names, routes (`/supplier`, `/fynix/suppliers`), database values (`supplier_fynix`, the `Supplier` role label from `app_group_candidates()`) and the spec keep "supplier". Two places translate a database value for display: `RoleChip` in `components/messaging/group-chat.tsx` and the sender chip in `message-flow.tsx`. Write "coordinator" in any new visible text.

**Client team, not hosts (owner decisions, 2026-11-26):** there is no host concept. Every active member of a client can be chosen for a meeting, on every campaign of that client, and a person who has set no hours counts as working Monday to Friday, 09:00 to 17:00 in the client's time zone (`withDefaultHours` in `lib/leads/host-hours.ts`). Nothing a person reads says "host": write "client team member". An agency sees the **name** of a client team member and nothing else (no job title, email or phone); the client and Fynix still see job titles. Code names keep the old word (`hostMemberId`, `host_hours`, `host_block`, `has_host`, the code `no-host`). The agency's list comes from the database function `app_campaign_team` (migration 0096) and the one check is `requireTeamMember` in `server/domain/host-availability.ts`; an agency reads a person's hours through `app_agency_serves_member`. The table `campaign_host` and the function `app_campaign_host_names` are no longer used and go in the clean-up phase. The page is `/client/hours` (Working hours, was `/client/hosts`) and the campaign tab is Client team (`/fynix/campaigns/[ref]/team`); both old addresses redirect. Spec: `docs/superpowers/specs/2026-11-26-calendar-and-meetings-design.md`; this was step B, plan `docs/superpowers/plans/2026-11-26-calendar-step-b-client-team.md`.

**Free time (calendar step C, migrations 0097 to 0099):** whether a slot is free is decided in one place, `lib/calendar/free-time.ts` (`isSlotFree`, `freeSlotStarts`, `freePeopleAt`: 48 hours of notice, working hours with the default week, typed blocks, busy time, at most 62 days). The table `meeting_attendee` holds invitations (`invited`, `accepted`, `declined`, `released`) and no runtime role touches it; `meeting.reply_due_at` and `meeting.confirmed_at` are empty until booking is built; they have an insert-only grant for the client and agency roles (0099) and no select, because Drizzle lists every column of the table in an insert and Postgres checks the privilege of each, so a new `meeting` column without that grant stops every booking. Busy time reaches a screen only through `app_team_people_for_campaign` and `app_team_busy_for_campaign` (migration 0100: a tenant never reads an organisation id, so a team is named by a campaign of its client, and the id versions `app_team_people` and `app_team_busy` are granted to nobody) (names, the client's time zone, and bare start and end times: a blocked time, a scheduled meeting, an open invitation before its deadline and an accepted one all look the same), read by `readTeamTimeForTenant` and `readTeamTimeForFynix` in `server/domain/team-availability.ts`. An agency reads the client's time zone through them because the default week is worked out in it, the same kind of fact as the zone of a person's own hours, which it already reads; the leak matrix lists the names and zones as allowed for those two read paths only (`allowedTokens`). Step F adds synced Google and Outlook time by replacing `app_team_busy`. Plan: `docs/superpowers/plans/2026-11-26-calendar-step-c-free-time-data.md`.

**Calendar pages (step D):** `/client/calendar`, `/agency/calendar`, `/coordinator/calendar` and `/fynix/calendar`, Month, Week and Day, read-only. State is in the address (`view`, `date`, `team`, where `team` is a campaign id that names the client). `server/domain/calendar-data.ts` (`loadCalendarForTenant`, `loadCalendarForFynix`) gives a page the choice of client, the team and its busy time, and the meetings the viewer may read: the client team member is named to the client and Fynix only, never an agency to a client, and the meeting link to whoever can read the meeting. The screen is `components/calendar/` and lays everything out in the viewer's own zone (`useViewerZone`); the rules for what each half hour is are in `lib/calendar/layout.ts` and the days and ranges in `lib/calendar/view.ts`. Not yet on screen: the agency filter for Fynix, and a person's own events from Google or Outlook (step F).

## Rules

- Work on `development`. `main` is production and only changes through a PR. Remote: `github.com/digibranders/fynix-leads` (private). Its default branch is `development`; `main` does not exist yet, so create it as the PR base when this goes to production.
- **Design:** the comps in `design-directions-v3/b-ledger-soft` are the visual authority ("Ledger Soft": tone and ring shadow, no outlines except on form controls). The owner rejected boxy outlined UI, borderless clutter and the earlier hybrid look. Never settle a design language from text alone: show a visual first. Layout switches by CSS breakpoints only, never by JavaScript.
- **Isolation:** the client never sees agency identity; the agency never sees client people, rep names or emails. Agency screens receive only the columns listed in the `agency*Columns` in `server/db/columns.ts` (read through `server/db/tenant-reads.ts`). When you add a screen, check the page source and its JavaScript chunks for forbidden names.
- **Logic:** domain rules live in `lib/` as plain TypeScript with tests next to them. Components render; they do not decide business rules. What counts and in which month is decided in one place, `lib/domain/counting-month.ts`: only an accepted lead (or a client no-show) adds one, in the month its meeting was held, read in the campaign's time zone (`COUNTED_STAGES`, `isCountedStage`, `countedMonth`). A rejection less than 24 hours before the meeting is still open with the owner and lives in `lateRejectionCounts`.
- **Copy:** sentence case, plain verbs, no exclamation marks, no em or en dashes in any text.
- **Database (`server/db/`, scripts in `scripts/`):** `lib/` stays pure and never imports `server/` or a database driver (`server/db/boundaries.test.ts` enforces it).
  - **Six login roles, one connection pool each, no `SET ROLE`:** `leads_owner` (migrations only), `leads_auth`, `leads_fynix`, `leads_client`, `leads_agency`, `leads_public`. Who connects decides what a request can see. Tenant requests go through `withOrgScope` (and Fynix through `withFynixScope`) in `server/db/scope.ts`, which sets `app.org_id` and `app.user_id` for one transaction. Never query a tenant pool any other way.
  - **Tenant roles never get a table-level grant.** `leads_client` and `leads_agency` hold `SELECT` on named columns only, so `select *` fails by design. Every tenant read starts from a typed column list in `server/db/columns.ts` through `server/db/tenant-reads.ts`. Do not write a Drizzle `select()` with no columns (the boundary test fails it).
  - **Every table** enables row-level security and gets a policy for each role that holds a grant, in the same hand-written `NNNN_<table>_grants.sql` migration. `server/db/structure.integration.test.ts` checks this for every table automatically.
  - **Views must be `WITH (security_invoker = true)`.** An ordinary view runs as its owner and bypasses row-level security. Materialized views are not allowed.
  - **Adding a table or column:** edit `server/db/schema/`, run `pnpm db:generate`, add a hand-written grants migration (`pnpm db:generate --custom --name=<table>_grants`), update the lists in `server/db/columns.ts` in the same commit, and add read paths and probes to `server/db/testing/leak-matrix.ts`. Migrations must be additive because a deploy migrates before it builds. Never edit an applied migration.
  - **Known limit:** a role can call `set_config('app.org_id', ...)` itself, so row-level security protects against a query bug, not against SQL injection into a tenant connection. Organisation ids are random UUIDs that tenant roles cannot read.
  - **Dev databases** are `fynix_leads` and `fynix_leads_test` on the Postgres 16 already running on this machine, shared with other projects. Create only those and the `leads_*` roles. The test harness refuses any database whose name does not end in `_test`.
- **Auth (`server/auth/`, rules in `docs/superpowers/plans/2026-11-12-phase-1b-auth.md`):** Better Auth 1.7.20, pinned exactly, email and password, no public sign-up.
  - **Better Auth stays inside `server/auth/`** and its HTTP handler is never mounted: sign-in, reset and account creation are server code calling `auth.api`, behind our rate limits (`server/auth/rate-limit.ts`, Postgres, `leads_public`, never inside a transaction) and our password policy (12 or more characters, not in a breach, `server/auth/breach-check.ts`). `server/auth/boundaries.test.ts` enforces it.
  - **Only `leads_auth` touches `session`, `account` and `verification`.** Fynix reads four columns of `user` (id, name, email, created time) and nothing else of it. The access matrix in `server/db/structure.integration.test.ts` lists, for every table, the roles that may touch it: adding a table or widening a grant means editing that list on purpose.
  - **Accounts are created only inside `withAccountCreationGrant`** (`server/auth/create-account.ts`), by `pnpm admin:create` and by invite redemption (`server/domain/redeem-invite.ts`). A user with no active `member` row gets no session.
  - **A request resolves like this:** `getSessionContext()` (cookie, session, `member`, organisation kind), then `withSessionScope(context, work)` (`server/auth/with-session.ts`), which picks the role pool and sets the scope. Sessions are fixed length: 14 days for client and agency, 12 hours for Fynix, never extended.
  - **Three Better Auth quirks, each guarded and tested:** a 403 in the user-create hook becomes a fake success (the hook returns `false`); a duplicate address answers with an id that was never stored (`createAccountWithGrant` reads the row back); a short secret falls back to a public default (`assertUsableSecret` refuses). Canary tests fail when a Better Auth upgrade changes any of them.
  - **Fynix second step (gate G1, built, off by default):** Better Auth's `twoFactor` plugin (TOTP and backup codes, no emailed code, no trusted devices) for Fynix people only. The services are in `server/auth/second-factor.ts` (`startEnrolment`, `confirmEnrolment`, `disableSecondFactor`, `verifySecondFactor`, each limited through `leads_public`), the actions in `server/auth/actions.ts` (enrol, turn off and backup-code use are audited as `member.two_factor_enable`, `member.two_factor_disable`, `member.backup_code_used`), the panel on `/fynix/profile` and the code page `/sign-in/verify`. `signInWithPassword` can answer `second-factor`. `REQUIRE_FYNIX_2FA=true` makes `requireFynix()` redirect a Fynix person without the step to `/fynix/profile` (only the layout and that page pass `allowWithoutSecondFactor`) and `runAction` refuse; tenant users are never affected. The `two_factor` table is `leads_auth` alone (migrations 0076, 0077). Recovery and rollout: `docs/deploy.md`.
  - **The reset link** is queued in `email_outbox` through `leads_public`, like every email (see Domain below). `pnpm mail:last` prints the newest message and its link in development.
  - **`x-real-ip`, not `x-forwarded-for`,** is the network address for rate limits. The production nginx must overwrite `x-real-ip` (phase 6).
- **Domain (`server/domain/`, `server/mail/`, rules in `docs/superpowers/plans/2026-11-12-phase-1c-domain.md`):** organisations, invites, terms, campaigns, members and aliases, as plain functions that take `DomainDeps` (`server/domain/deps.ts`). The running app builds it with `getDomain()` (`server/domain/index.ts`).
  - **Every Fynix write goes through `fynixWrite`** (`server/domain/fynix-write.ts`): the Fynix scope transaction plus an `audit` function that appends to `audit_log` in the same transaction. The database backs it: a transaction as `leads_fynix` that changes a domain table without an audit row cannot commit (`audit_required`), and `audit_log` refuses UPDATE and DELETE for every role including the owner. A new table Fynix can write needs the `audit_required` trigger in its grants migration (a structural test fails without it).
  - **Only a Fynix admin changes set-up** (rules in `docs/superpowers/plans/2026-11-13-phase-1d-fynix-setup.md`). Admin is `member.role = 'manager'` in the Fynix organisation, staff is `member`. `fynixWrite` refuses staff with `admin-required`, and a statement trigger (`fynix_admin_required`, migration 0029) on every table Fynix can write, except `audit_log` and `email_outbox`, refuses them in the database too; a structural test fails for a new Fynix writable table without it. `fynixRead` is open to staff. Staff work on leads (phase 2) needs its own entry point and tables without the trigger.
  - **Hierarchy and set-up tables (1D):** a supplier is an agency with no parent (`organisation.parent_org_id` null), a partner agency is an agency whose parent is a supplier, two levels at most, all enforced by constraints and triggers. `campaign.agency_org_id` is the supplier, and the database refuses a partner agency there. `campaign_share` goes to the supplier or one of its partner agencies; `campaign_host` is no longer used (see the client team note above); `agreement` versions are never edited, only superseded (versions count per campaign and party). Since phase 1E (migration 0032 and later) the tenant roles hold narrow grants on these tables and columns; each is in the access matrix and the leak matrix.
  - **Nothing is deleted,** with three exceptions that are settings, not records: `campaign_share`, `host_hours` and `host_block` rows are removed when a share, a weekly set of hours or a blocked time is removed, and the audit row keeps what they were. Organisations and campaigns are archived by status, invites are revoked, terms and agreements are superseded, members are suspended. Audit snapshots (`server/domain/snapshots.ts`) never hold a token, a hash, a link or a password.
  - **Invites:** a 32 byte token, only its SHA-256 stored, seven days, one live invite per address (issuing a new one revokes the old one in the same transaction). `leads_auth` sees an invite only when its transaction names the hash (`withInviteHash`). Redemption (`redeemInvite`) is one transaction on `leads_auth` with Better Auth running on it, so the account, the membership, the alias, the acceptance of the terms and `redeemed_at` commit together or not at all.
  - **The accept-invite page** reads through `loadInvitePage` (`server/domain/page-data.ts`) and posts to `redeemInviteAction` (`server/domain/actions.ts`), which redeems, signs the person in with the password they chose and lands on `/welcome`. Pages import nothing else from `server/domain`.
  - **Terms:** a published document is never edited. The text seeded by `pnpm terms:placeholder` is PLACEHOLDER (gate G2): on an https deployment no invite is issued while a party's current terms are placeholder.
  - **Email:** every message is written to `email_outbox` first (`enqueueEmail`) and sent by `drainOutbox` (`pnpm outbox:run`, as `leads_auth`) through Brevo from `hello@fynix.digital` (or `MAIL_SENDER_ADDRESS` once set). The link lives in its own column, only while the row is `pending`, and is cleared on send, on a permanent failure, on cancel and by the purge after a day; the stored copy of the text has no link. Without `BREVO_API_KEY` development only writes the table, and an https deployment refuses to start without a key. A failure to send is recorded and retried (five attempts, backing off), never thrown into a request. Tests use `FakeTransport` and never call Brevo.
- **Meetings:** `meeting.google_meet_url` is null until a real room exists. Never generate one: Meet codes are only issued by Google, so an invented address points at no room. The screens show "Link to follow". Since phase 6 chunk A the link comes from `MeetProvider` (`server/meet/`): `none` by default (no room, no call to anyone), `google` when `MEET_PROVIDER=google` (Meet REST API v2, an `OPEN` space per booking, made before the booking transaction opens by `createRoomSafely`, so a failure leaves the link null and never fails the booking; the link and `google_space_id` are written by `bookMeeting` and survive every postponement). `google_space_id`, `ics_sequence` and `join_imported_at` are never readable by a tenant. The browser calendar file in `components/meetings/meeting-actions.tsx` is still the old one (its id ends in `@fynix.digital`): the screens phase swaps it for the server's.
- **Launch emails (phase 6 chunk A, migrations 0073 to 0075, off by default):** `LAUNCH_EMAILS_ENABLED` (exact word `true`) and `MEET_PROVIDER` (`none`/`google`) are the two switches; with both unset the app sends the three account emails exactly as before and writes nothing else. `notify()` (`server/domain/notices.ts`) now also calls `enqueueLeadEmails` (`server/mail/lead-emails.ts`) in the same transaction, which writes nothing while the switch is off. Who gets which email is `lib/leads/lead-emails.ts` (pure, tested against the table in `docs/superpowers/specs/2026-11-24-meetings-and-email-decision.md`); the texts are `lib/email/launch-templates.ts` (one template per audience and event; prospect letters are the `prospect_*` ones) on the shell in `lib/email/design.ts`, the only file that may hold a colour or a table. The people, the person who acted (never emailed) and everything only the database may read are resolved by the SECURITY DEFINER functions of 0075 (`app_enqueue_lead_email`, `app_lead_email_context` and their `_system` twins for the sweep): a prospect letter gets the client's brand, the privacy link, the alias name and title added to its params by the database, goes out under the alias's name from the neutral address (`MAIL_SENDER_ADDRESS`), replies to the alias mailbox, and is queued only for a campaign with `prospect_email_enabled` and `client_privacy_url` (Fynix admin: `setCampaignPrivacy`, `setProspectEmail` in `server/domain/campaign-privacy.ts`; the client reads both, no agency reads either). A prospect email never names Fynix, the coordinator, an agency or the portal, and carries no portal link; a message with link rule `none` (`linkRuleFor`: the prospect letters) may carry a Meet link in its body only if it is https on `meet.google.com`. The outbox sender refuses a prospect letter from an address that names Fynix and skips launch templates while the switch is off. Every meeting email carries an `.ics` made at send time (`lib/email/ics.ts`: fixed id `<meeting ref>@leads.invalid`, SEQUENCE from `meeting.ics_sequence`, which a trigger raises on every move or cancel). Time-based emails and the join import are the steps of `pnpm leads:sweep` in `server/mail/launch-sweep.ts` (`meeting_reminder`, `lead_reminder.email_sent_at`, `meeting_join`). What the owner must do before any of it is turned on: `docs/launch-checklist.md`.
- **Pending emails (2026-11-25, migrations 0087 to 0093, behind the same `LAUNCH_EMAILS_ENABLED` switch; design `docs/superpowers/specs/2026-11-25-pending-emails-design.md`):** the client is emailed on an automatic acceptance, a rejection Fynix changed (with the note, and a bell notice) and a client no-show; a proposal of new times, a contest, its decision and a review request send an email too. `app_email_enqueue` no longer lists template names: a new template is a value of the `email_template` enum (in its own migration), an entry in `LAUNCH_TEMPLATES`, a sample and a catalogue entry in `lib/email/samples.ts`, and nothing else. So every value of that enum but the three account emails can be queued for the people of a lead by anyone who may act on that lead: an email that must not be, needs its own function and a line in that exception. A campaign may have its own opening paragraph for the confirmation letter (`campaign.prospect_letter_opening`, Fynix alone reads and writes it, `setProspectLetterOpening`, rules in `lib/email/letter-opening.ts`; a company is matched by its name without the legal ending, `nameCore` and `app_name_core`, held equal by a test): it is checked when saved, by `app_prospect_letter_opening` when the letter is queued and again when it is rendered, and a paragraph that fails is left out so the default letter goes. Targets: `claimTargetNotices` (`server/mail/lead-emails.ts`) runs from `notify()` after every event that can make a lead count and from the sweep after an automatic acceptance; the database function `app_claim_target_notices` counts with `app_counted_stages()` (held equal to `COUNTED_STAGES` by a test) in the month of the meeting in the campaign's zone, takes an advisory lock named after the campaign (never a row lock: the caller already holds the lead's row), stamps each met target in `once_stamp` so it is said once, writes the bell notice (kind `general`, not behind the switch) and returns what to email. A lead beyond its sender's share tells Fynix (`lead_over_share`, from both submit paths). A new agreement version emails the managers of both sides through `app_enqueue_campaign_email`, the only email keyed on a campaign and Fynix's alone to queue. The sweep's `sendWaitingReminders` reminds a client once a local day, between 9 am and 8 pm there, of leads waiting over 24 hours for a time (measured from `lead.updated_at`; a lead the client has asked other times for is left out, `app_leads_waiting`), and sends Fynix one summary in its own transaction. A time zone typed wrong never stops anything: `app_safe_zone` falls back to Europe/London.
- **Operations:** `docs/deploy.md` is the server checklist (nginx must overwrite `x-real-ip` and cap bodies per route; `pnpm outbox:run` every minute and `pnpm ratelimit:purge` daily). Every response carries the headers in `lib/http/security-headers.ts`. Posting a message, attaching files and submitting a lead are rate limited per user (`lib/auth/rate-limit-rules.ts`). A CSV cell that starts with `=`, `+`, `-` or `@` is written as text (`toCsv`).
- **Deploys:** live at `leads.fynix.digital`. Merging to `main` deploys within a minute and migrates before the build (`vps-setup/fynix/leads/`). It holds test data only (owner, 2026-11-24). Merge at the end of a phase, on the owner's word. The build order is `docs/superpowers/plans/2026-11-24-build-roadmap.md`.
- **Fynix screens (`app/(fynix)/fynix/`, `components/fynix/`, `server/fynix/`, plan `docs/superpowers/plans/2026-11-13-phase-1d-admin-screens.md`):** suppliers, campaigns, agreements and shares, hosts, for a signed-in Fynix member.
  - **Who gets in:** `requireFynix()` (`server/fynix/session.ts`) runs in the shell and in every page, because a layout does not run again on navigation. No session goes to sign-in, a client or agency session gets the not-found page. `/welcome` sends a Fynix session to `/fynix`.
  - **Reads** are the role-shaped Fynix reads in `server/domain` (`supplier-overview.ts`, `campaign-overview.ts`), open to staff. Pages call them with `getDomain()` and the actor from `requireFynix()`. Selection is in the URL (`?supplier=`, `?host=`).
  - **Writes** are the actions in `server/fynix/actions.ts`, thin shells over `runAction` (`server/fynix/run-action.ts`): session, the domain's own zod schema for field errors, the domain function, plain-words refusals (`server/fynix/errors.ts`), then `revalidatePath("/fynix", "layout")`. Staff see no write control and the domain still refuses them (`admin-required`). Every export of `actions.ts` is a public endpoint, so it exports only actions.
  - **Forms** open in a panel-sized sheet (`components/fynix/forms/`), built from the sign-in form parts. Plain text for hours, blocked times and dates is in `lib/fynix/` with tests.
- **Audit log and email templates (phase 7, Fynix admins only; staff get the not-found page and no menu item, `adminOnly` in `components/shell/nav.ts`):** `/fynix/audit` reads `listAuditLog` (`server/domain/audit-overview.ts`, refuses staff itself) with filters in the address (`lib/fynix/audit-filter.ts`). `/fynix/templates` previews every template from fake data (`lib/email/samples.ts`) in a sandboxed `srcDoc` iframe and shows the result of `checkEmailInvariants` (`lib/email/invariants.ts`, the same check `templates.test.ts` runs). Wording is changed in code, never on that page.
- **Dev server:** `pnpm dev` serves http://localhost:3020. Next.js allows one dev server per project, so reuse the running one. Do not stop a server unless the owner says so.

With:

```markdown
pnpm db:seed            # two clients, two agencies, four campaigns (refuses a non-empty database)
pnpm db:generate        # SQL from server/db/schema/; add --custom --name=<name> for hand-written SQL
pnpm admin:create --email=<address> --name="<full name>"   # the first Fynix admin; asks for the password
pnpm mail:last          # prints the newest message in the dev email outbox (a reset or invite link)
pnpm outbox:run         # sends what is waiting in the outbox once (needs BREVO_API_KEY; without it nothing is sent)
pnpm terms:placeholder  # writes PLACEHOLDER terms for any party that has none (development only)
```

Before calling a change done, run lint, typecheck, test and build. Add `pnpm test:integration` when the change touches `server/db/`, a migration or a grant.
